REMOTE CANDIDATE QUALIFICATION
btcminer.provider_jobs.RemoteCandidateWorker is an isolated opt-in adapter.
It requires an explicit header, target, work revision and nonce. It binds target
and revision to job identity; checks both remote SHA stages; independently
recomputes the result locally; and only then compares the digest with the exact
target. Nothing in this adapter submits a block or controls the active miner.

Changing jobs invalidates in-flight results. Cancellation/deadline checks occur
before and after each request and before publishing a result. Socket timeouts
are bounded by remaining time; a late response is discarded. This does not claim
instant interruption of an operating-system network call. Transient retries
are bounded, permanent/integrity failures are not retried, and request attempts,
retries and completed candidates are counted separately. A128-entry cache avoids
recent duplicate computations within one worker/job; it is not durable exactly-
once execution or a promise of deduplication after eviction/process restart.
The five-second default deadline and retry bounds govern this optional remote
operation only. They do not restrict the production miner's nonce search.

Example, from Python with an explicit public/test header:
  from btcminer.provider import ProviderClient
  from btcminer.provider_jobs import RemoteCandidateWorker
  client = ProviderClient(timeout=3)
  client.authenticate()
  worker = RemoteCandidateWorker(client)  # exclusively owned client
  worker.bind(header_bytes, exact_integer_target, 'work-revision-1')
  result = worker.check(nonce, seconds=5, retries=1)

result.meets_target is candidate qualification, not network acceptance. The
production miner still uses its existing ARM SHA256 backend and nonce strategy.
The adapter does not implement a remote mining-job server or persistent queue.

DEPLOYMENT AND REMAINING PROVIDER LIMITS
Only the research observer was reloaded. The old and new analysis sources were
checked byte-for-byte, except for the three changed Store ingestion methods;
the remaining Store AST is identical. The unchanged analysis checkpoint was
explicitly reused with archived original bytes and a source-equivalence witness.
Existing observations retain their original analysis versions; they are not
relabeled as newly verified. New records use the new source version. The existing
backlog stays explicit; this does not assert instantaneous full-history analysis.

Provider-side inverse trig support, direct sha256 expressions, percent syntax,
scientific-literal parsing and the phi identity's finite certification limitation
are unchanged external issues. This client cannot deploy fixes to that server.
Existing workarounds remain explicit: numeric-string variables for scientific
notation, floor-based remainder for its stated domain, the two-call integrity-
hash route for SHA256d, and separate local exact algebra for the phi identity.
Unsupported provider computations are never silently filled with local answers.
