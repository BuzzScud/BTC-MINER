THESIS PROVIDER INTEGRATION — 2026-10-12

AUTOMATIC MINING-SESSION INTEGRATION

provider_enabled=on starts a dedicated provider process with the mining engine.
provider_user selects the configured account. Portable installs default off
with an empty account and endpoint until configured.
The process refreshes capabilities and the account's formula catalogue every five
minutes, receives TCMP WebSocket model events, and checks one sampled flower/rod
offset for each new mining job, at most once every ten seconds. Results are tied
to both the engine session and the job fingerprint. Old-session results cannot
mark a new job checked. Offline, stale, pending and mismatched results stay visible.

The Copper mining-loop panel shows API connection, stream and job-math status.
Full counters are available in status --json under provider. A stopped console
shows that the API will connect when you start. The process stops with the miner.
Bounded files are stored in logs/provider-runtime/. Only scalar traversal inputs
are sent for calculation; no payout, wallet, credentials or full header is sent.

These API features run automatically during mining. They validate sampled job
arithmetic and supply provider model information. Native hashing and nonce
coverage remain local; the provider does not predict winners or exclude nonces.
No network operation runs in the hash-worker or coordinator thread.

The miner now includes an explicit provider client. From the Copper console:

  /provider capabilities
  /provider refresh
  /provider formulas --query rod
  /provider calculate --expression '11*15*17'
  /provider watch --seconds 10
  /provider check --output validation/provider-check.json

In a shell, use ./bin/btc-miner provider ... (without the leading slash).
The refresh command saves a dated observation to logs/provider/latest.json.
--output PATH saves full redacted JSON for any command. Refresh prints a compact
summary. Formulas, calculations and watch return provider data for inspection.
Watch lasts at most 60 seconds, accepts at most 200 events, and caps the combined
decoded snapshot at 16 MiB. A missing sessionReady, disconnection, provider error,
corrupt frame or oversized response fails explicitly. It never replays writes.

AUTHENTICATION

Run ./bin/btc-miner provider login (Windows: .\btc-miner.cmd provider login) in an
interactive terminal. The wizard prompts for the endpoint, existing account and
hidden password, verifies account identity, saves only nonsecret configuration,
and opens the dashboard. It does not start mining. Passwords and tokens are not
saved to disk; the password is retained in the dashboard's process environment
and inherited by its miner processes for dedicated sessions and reconnects.
Repeat provider login when reopening. Account creation/recovery belongs to the
provider website. Stop the miner before changing accounts. Closing the dashboard
does not stop a miner you explicitly started.

Public capabilities do not require credentials. For automation supply
BTC_PROVIDER_URL, BTC_PROVIDER_SESSION and --user (or BTC_PROVIDER_USER for CLI
commands); runtime identity is configured with provider_user. Alternatively
BTC_PROVIDER_PASSWORD allows a fresh login to BTC_PROVIDER_URL. A preexisting
macOS Keychain session/password can still be used, bound to account and origin.
Explicit tokens are never silently replaced with a password login after a 401.
Credentials are never command arguments, JSON snapshots, terminal output or
release inputs. Remote endpoints require HTTPS; loopback HTTP supports trusted
local tunnels. HTTP/WebSocket redirects and environment HTTP proxies are refused.
The saved provider_url is used by the mining runtime unless BTC_PROVIDER_URL
overrides it. Standalone provider tools remain independent of miner settings.

TRANSPORT AND MEASUREMENTS

The Python implementation supports TCMP v1 with the current five CRT variants,
including packed/adaptive rod sets, and legacy stored/RLE/LZ77/blocked-LZ77/delta
frames. Decode checks length before allocation, structure and the provider's FNV
checksum. This checksum detects corruption; it is not a cryptographic authenticator.
HTTP negotiates x-app-accept-encoding: tcmp. WebSocket negotiates enc=tcmp and
accepts both text JSON and binary TCMP frames. Outgoing JSON uses TCMP only if its
complete frame is smaller. No remote compression call enters the mining path.

The check command measures 15 synthetic codec cases: three inputs across five
modes. It verifies Python/server byte equality and both directions of decoding.
It also compares ten exact calculator results with independent Python arithmetic,
including a value above 2^53, negative floor, a perfect square, a fraction, the
Eisenstein norm and flower-count examples. Failures produce a nonzero exit status.
Reported network duration, local codec time and byte counts have distinct labels.
These are finite observations, not an end-to-end mining benchmark.

SOURCE AND PROOF SCOPE

Canonical source: src/tools/provider.py, provider_runtime.py and tcmp.py.
btcminer/provider.py and btcminer/tcmp.py are compatibility links.
ProviderClient.updates() is an async iterator for modelSnapshot, forensicEvent,
calculationTelemetry and other protocol messages. It requires optional aiohttp;
all REST and codec commands use the Python standard library. The optional
dependency is imported only when watching; base miner startup does not require it.

Provider labels, formula statuses and event receipt do not change the miner's
proof registry or candidate rules. The new client performs discovery, calculation,
synthetic codec checks and observation; it submits no issue requests or files.
Provider requests do not change worker settings. Stop remains able to
interrupt a provider diagnostic from the Copper console.
