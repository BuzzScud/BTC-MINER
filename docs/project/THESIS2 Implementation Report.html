What is delivered

BTC MINER is a folder-based application with an interactive terminal dashboard, scriptable commands, a native Apple Silicon SHA256d library, Bitcoin Core solo mining, and Bitcoin Stratum V1 pool support. The terminal follows the local XMR MINER reference’s ledger, right rail and command controls.

Version 1.1 adds thesis2 as the default strategy for a fresh configuration. The supplied HTML is included unchanged, its mathematical operations are ported to Python, and the clock/field/CRT operations are composed into a new nonce traversal. The existing thesis, linear and hybrid strategies remain available.

2 workersConservative default, adjustable CPU use

Scope of the math integration. The HTML describes mathematical constructions; it does not supply a Bitcoin mining algorithm. The implementation ports those constructions and adds an explicitly application-defined traversal, btc-traversal-v1. Its correctness and mining performance are not established by the source’s theorem counts.

Deliverables: this report; the complete miner folder; BTC MINER - M2.zip alongside the folder; source reference; README; source notes; and a SHA-256 file manifest. The original backup and XMR MINER project were not modified.

The source mathematics, mapped to code

All twelve sections of the supplied reference are represented as implemented mathematical operations or attributed source-status information. The module is btcminer/thesis2.py. Integer arithmetic uses exact Python integers. Trigonometry, distances and packing fills use floating point.

How the new mining strategy is connected

01 · INPUTActual 76-byte header prefix
02 · ORDERField cycle + clock phases + CRT tiles
03 · HASHBounded native SHA256d batches
04 · SUBMITRehash candidate, check target, submit work
  1. Seed a job-specific ordering. Hash a versioned domain separator and the first 76 bytes of the actual block header. Interpret the first eight digest bytes as a little-endian integer. The nonce bytes are excluded. Divide that seed into clock, field, cell and starting-tile phases.
  2. Order the field cycle. Visit powers of 1 + 3i at exponents (phase + k × step) mod 360. The step defaults to 7 and must be coprime to 360. Map the nonzero field coordinates to labels a + 19b − 1, giving labels 0 through 359. Reconstruct each label through the small CRT wheels.
  3. Build one 144000-value tile. Visit 400 cells using (cell_phase + i × prime) mod 400. Combine each cell with the 360 ordered residues, add the job phase, and reconstruct with the (128, 9, 125) wheels. The tile stores 144000 unsigned 32-bit offsets: 576000 bytes on the target Mac.
  4. Traverse the uint32 domain. Cycle through 29827 tiles from the header-derived starting tile. The last tile has 23296 valid values; larger offsets in that tile are skipped instead of wrapped. The ordering is designed to visit each of the 2³² nonce values once if the round finishes.
  5. Feed the existing hashing engine. Produce bounded lists, normally 16384 candidates per batch, for the worker threads. The miner counts attempted hashes and resumes unscanned batch tails after pool shares. Python SHA256d rechecks found candidates before submission.
  6. Respect the current work and user controls. Job changes, connection validity, stop/pause controls and session/round limits can end a traversal early. A fresh header receives fresh phases. single_nonce_only uses the first THESIS2 nonce.

The field ordering is a permutation, the prime step permutes the 400 cells, and a clock phase is a modular translation. Together with disjoint tiles, these are the design basis for full coverage. This explanation is a construction argument, not an executed coverage test or a formal proof of the implementation.

The source does not prescribe the seed, label mapping, 400-cell construction, tile scheduling or Bitcoin adapter. Those are new integration decisions. CRT reconstructs the clock positions; it is not a hash predictor. No mining speedup or measured M2 throughput is claimed.

Inspector context: math inspect uses a synthetic header and identifies it as such. Live mining seeds the traversal from the actual header. Historical analysis uses each published block’s recorded header and reports where its nonce would occur in this ordering. Full-domain membership is automatic; rank is not a prediction of future success or live multiworker completion order.

Preserved controls: legacy entropy bounds, candidate partitions, recurrence, hybrid tail and optional recovery remain available in their legacy modes. THESIS2 has its own validated step/prime controls; those legacy candidate filters do not run inside the new strategy.

Logging: THESIS2 records bounded job metadata and the first 20 ordered nonces in logs/thesis2-nonces.jsonl. SUPT mode buffers and comparisons distinguish thesis2 from thesis, linear and hybrid. Existing events, counters and session summaries remain available.

Moving the package to the M2

  1. Copy the entire BTC MINER folder, or unzip BTC MINER - M2.zip, into a writable folder on the Mac mini. Keep all contents together.
  2. Ensure Python 3.9 or newer is available. There are no pip dependencies. The arm64 SHA256d library is already included; a compiler is only needed if it must be rebuilt.
  3. Open BTC Miner.app or Start BTC Miner.command. Opening the dashboard does not start mining. Use /setup to choose Core or a Bitcoin Stratum V1 pool and enter the connection details.
  4. Use /strategy thesis2 if bringing an existing configuration that selected another mode. A fresh configuration already defaults to THESIS2. Press s when ready to start.
  5. Press t to stop and save a Desktop summary. q and Ctrl+C detach the view while an explicitly started miner continues running.

Defaults target the M2 with 8 GB RAM: two worker threads, lower process priority and hashing paused until 120 seconds after keyboard/mouse activity. Adjust with /perf, /pause, or /set cpu_duty=50. Worker percentages select a fraction of logical CPUs; they are not an exact system-wide utilization cap.

Bitcoin Core must be installed and running separately with RPC enabled. Pools must support Bitcoin SHA256d Stratum V1 and accept the worker’s share rate/difficulty. No default payout address or pool is embedded. The package asks for no seed phrase or private key.

Connection recovery follows the local CLI design: retry, configured backup pool, periodic primary retry, and stale-work invalidation. A lost submission response is recorded as unknown instead of blindly resubmitted. Closing the dashboard preserves the local daemon; reboot recovery is manual and no login service is installed.
